# rle565

Compact run length encoded images for RGB565 displays, with a fast
compositing renderer in portable C.

rle565 is aimed at embedded and microcontroller projects that draw UI
artwork (icons, buttons, gauges, overlays, anti-aliased shapes) onto 16-bit
RGB565 framebuffers. Images are encoded ahead of time from PNG with a
Node.js tool, stored in flash, and drawn directly from there, with alpha
blending, clipping, global fade and on-the-fly recoloring, without
decompressing into RAM first.

```
PNG ──► rle565 encoder (Node.js) ──► .rle565 file ──► draw_image() (C) ──► RGB565 framebuffer
```

## Features

- **Small files.** Palette plus run length encoding. Transparent rows at the
  top and bottom are trimmed. Typical UI artwork packs to a few percent of
  its raw RGB565 size (see [numbers below](#compression-examples)).
- **Draw straight from flash.** `draw_image()` reads the encoded data in
  place and never writes to it, so images can live in read-only or
  memory-mapped flash.
- **Full alpha.** Each pixel can be opaque, transparent, or partially
  transparent (premultiplied 8-bit alpha). Anti-aliased edges and soft
  shadows blend correctly over whatever is already on screen.
- **Global alpha.** Fade any image in or out with a single 0-255 alpha
  value, combined with per-pixel alpha.
- **Clipping.** Draw any sub-rectangle of an image at any position. Images
  are clipped to the destination buffer, or to a clip view of it.
- **Save and restore.** Optionally capture the framebuffer pixels an image
  overwrites, then put them back later with `restore_image()`. Useful for
  cursors, popups, highlights and other temporary overlays without redrawing
  the whole screen. The worst case capture size is computed by the encoder
  and stored in the image.
- **Recoloring.** Swap in a different palette when drawing, or use
  `recolor_palette()` to tint a greyscale or single-color image to any
  two-color gradient at runtime, so one asset can serve many colors.
- **Shared palettes.** Encode a set of images against one common palette and
  supply it at draw time, so the palette is stored once.
- **Fast.** 32 specialized drawing loops, one per combination of features,
  so the per-pixel code never checks for features an image or draw call
  doesn't use. The loops are generated by a script so they stay consistent.
- **Accurate blending.** Blends round to nearest and work at each channel's
  native precision, so blending a color over itself leaves it unchanged.
- **Text.** Pre-rasterized anti-aliased fonts with kerning, built from
  [msdf-atlas-gen](https://github.com/Chlumsky/msdf-atlas-gen) output and
  drawn with a fast alpha mask renderer.
- **Safe decoding.** A bounds-checked decoder (C and JS) for tooling and
  previews that rejects corrupt or malicious files instead of crashing.
- **Tooling.** A command line encoder/decoder, a JavaScript API, and a
  Windows Imaging Component codec so `.rle565` files show thumbnails in
  Windows Explorer.

## Why rle565

Small displays driven by microcontrollers usually use RGB565 framebuffers
and have little RAM and limited flash. The common options for artwork all
have drawbacks:

| Approach | Problem |
|---|---|
| Raw RGB565 bitmaps | Large (2 bytes per pixel), no transparency |
| RGB565 plus a separate alpha mask | Larger still, and blending every pixel is slow |
| PNG or other general purpose formats | Need a decoder, working RAM, and CPU time to decompress before drawing |

rle565 is designed around how UI artwork actually looks: large areas of flat
color and transparency, a limited number of distinct colors, and alpha only
around edges. Runs of identical pixels are stored once, transparent runs are
skipped without touching the framebuffer, opaque pixels are stored as
ready-to-write RGB565 values, and only partially transparent pixels pay for
blending. Decoding happens while drawing, so no intermediate buffer is
needed.

### Compression examples

The 300×300 test images in `test/artwork` (raw RGB565 would be 180,000 bytes
each):

| Image | Content | Palette | Encoded size | % of raw RGB565 |
|---|---|---|---|---|
| `square` | Opaque square on transparent background | 2 colors | 2,212 bytes | 1.2% |
| `transparent-square` | Semi-transparent square | 2 colors | 2,212 bytes | 1.2% |
| `circles` | Four anti-aliased colored circles | 612 colors | 9,376 bytes | 5.2% |
| `grey-gradient` | Full-size diagonal grey gradient | 17 colors | 10,799 bytes | 6.0% |
| `red-circle` | Circle with a radial gradient and soft edge | 290 colors | 47,364 bytes | 26.3% |

Smooth gradients compress least, because neighboring pixels rarely repeat.
Flat, iconic artwork compresses best.

## Quick start

1. Install the encoder's dependencies. Needs Node.js 18.17 or later (the
   minimum for [sharp](https://sharp.pixelplumbing.com/), used for image
   loading). Tested with Node.js 24; a current LTS release is recommended.

   ```
   cd encoder
   npm install
   ```

2. Encode your artwork:

   ```
   node encoder/cli.js -d assets/ icons/*.png
   ```

3. Add `src/rle565.c`, `src/rle565.h` and `src/rle565.core.h` to your
   firmware or application, and draw:

   ```c
   #include "rle565.h"

   extern const uint8_t icon_rle565[];   // the .rle565 file in flash, 4-byte aligned
   static uint16_t framebuffer[320 * 240];

   IMAGE_BUFFER screen;
   init_image_buffer(&screen, 320, 240, framebuffer, 0);

   draw_image(&screen, icon_rle565,
              10, 20,                                   // destination x, y
              0, 0,                                     // source x, y
              get_image_width(icon_rle565),             // source width
              get_image_height(icon_rle565),            // source height
              NULL,                                     // no capture
              255,                                      // fully opaque
              NULL);                                    // image's own palette
   ```

## Encoding images

### Command line

```
node encoder/cli.js [options] <input...>
```

Run `npm link` in `encoder/` to install it as an `rle565` command.

Each input is converted according to its extension: `.rle565` files are
decoded to PNG, `.json` files (msdf-atlas-gen layouts) are packed as fonts
(see [Fonts and text](#fonts-and-text)), and anything else is encoded to
`.rle565`. A single run can mix them.

| Option | Description |
|---|---|
| `-o, --output <file>` | Output file (single input only). Default: the input name with `.rle565` (encoding), `.png` (decoding) or `.rfnt` (fonts) |
| `-d, --outdir <dir>` | Output directory. Default: next to each input. Relative `--output` and `--shared-palette` paths are resolved against it. Missing directories are created |
| `-b, --background <bg>` | Composite over a background before encoding: a `.png` file, or a color as `#RRGGBB`, `0xRRGGBB` or `RRGGBB` (encoding only) |
| `-a, --alpha-rect <x,y,w,h>` | Area that keeps its own alpha instead of being baked over the background. Repeatable (encoding only) |
| `-p, --shared-palette <file>` | Build one palette from all inputs, write it to `<file>`, and leave it out of each image (encoding only) |
| `-P, --palette <file>` | Palette file to decode images that use a shared palette (decoding only) |
| `-A, --atlas <file>` | Atlas image for a font (single font only). Default: the `.json` name with `.png` |
| `-D, --default-char <char>` | Character drawn for characters missing from the font. Default: U+FFFD or `?` |
| `-v, --verbose` | Print encoding statistics |
| `-h, --help` | Show help |

Examples:

```bash
# Encode next to the source files
node encoder/cli.js icons/home.png icons/settings.png

# Encode into a build folder, with statistics
node encoder/cli.js -v -d build/assets icons/*.png

# Pre-blend onto the known screen background color
node encoder/cli.js -b "#202830" -d build/assets panel.png

# ...but keep real alpha inside a region that's drawn over changing content
node encoder/cli.js -b bg.png -a 40,40,200,60 -d build/assets panel.png

# A set of images sharing one palette
node encoder/cli.js -p icons.pal -d build/assets icons/*.png

# Pack a font rendered by msdf-atlas-gen (reads myfont.png too)
node encoder/cli.js -d build/assets myfont.json

# Decode back to PNG to check the result
node encoder/cli.js -d check/ build/assets/*.rle565
node encoder/cli.js -P build/assets/icons.pal -d check/ build/assets/home.rle565
```

With `--verbose`, each image reports its size, the range of stored rows,
palette size, run statistics, encoded size as a percentage of raw RGB565,
and the capture buffer size.

### Background baking

Partially transparent pixels are the most expensive to store and draw, and
increase palette size. If you know what an image will be drawn over, such
as a fixed screen background color or image, `--background` blends the
artwork over it at encode time. Edge pixels then become opaque and are
drawn with a simple store.

Fully transparent pixels stay transparent, so the image keeps its shape.
Areas listed with `--alpha-rect` keep their original alpha, for parts of an
image that sit over content that changes at runtime.

A background image must be at least as large as the artwork. They're
aligned at the top left.

### Shared palettes

`--shared-palette` collects the colors of every input into one palette,
written as a separate file (a 32-bit little endian count followed by the
32-bit entries, the same layout as the `PALETTE` struct). Each image is
encoded without its own palette, and the palette is passed to `draw_image()`
at runtime. This saves space when many images use the same colors, such as
a family of icons.

### JavaScript API

The encoder modules are ES modules and can be used directly from build
scripts:

```js
import fs from "node:fs";
import { packRle, packPalette, PaletteBuilder, quantizePngTo565 } from "./encoder/pack.js";
import { unpackRle, unpackRleToPng, readPalette, readRleHeader } from "./encoder/unpack.js";
import { blobPack } from "./encoder/blobpack.js";

// Encode a PNG (path, or { data, info } raw RGBA from sharp)
const packed = await packRle("icon.png", {
    background: 0x202830,             // number (RGB), PNG path, or raw image
    alphaRects: [{ left: 0, top: 0, width: 32, height: 32 }],
});
fs.writeFileSync("icon.rle565", packed.data);
console.log(packed.packedSize, packed.compressionRatio, packed.captureSize);

// Shared palette across several images
const builder = new PaletteBuilder();
for (const f of files) await packRle(f, { paletteBuilder: builder });  // first pass collects colors
const palette = builder.finalize();
fs.writeFileSync("shared.pal", packPalette(palette));
for (const f of files) { const p = await packRle(f, { palette }); /* p.data ... */ }

// Decode
const image = unpackRle(fs.readFileSync("icon.rle565"));    // { width, height, data: RGBA Buffer }
await unpackRleToPng(fs.readFileSync("icon.rle565"), "icon.png");

// Bundle several images into one file (read in C with blobpack.h)
fs.writeFileSync("assets.bin", blobPack([imageA.data, imageB.data]));
```

`packRle()` returns the encoded `data` along with statistics: `width`,
`height`, `paletteSize`, `hasPartialAlpha`, `firstRow`, `rowCount`, run and
pixel counts by run type, `packedSize`, `compressionRatio` and
`captureSize`.

`quantizePngTo565(file)` rewrites a PNG in place with its colors reduced to
RGB565 precision, which is handy for previewing exactly what the encoder
will produce.

## Using the C library

The library is three files: `rle565.c`, `rle565.h` and the generated
`rle565.core.h`. It is plain C (C99 or later, also compiles as part of a
C++ project) with no dependencies beyond the standard C headers.

### Framebuffers

```c
IMAGE_BUFFER screen;
init_image_buffer(&screen, width, height, pixels, stride);   // stride in pixels, 0 = width
```

`clip_image_buffer()` creates a view of a rectangle within another buffer.
Drawing into the view is clipped to that rectangle, and coordinates are
relative to its top left corner:

```c
IMAGE_BUFFER panel;
clip_image_buffer(&panel, &screen, 100, 50, 200, 120);
draw_image(&panel, icon, 0, 0, 0, 0, w, h, NULL, 255, NULL);   // drawn at (100, 50) on screen
```

### Drawing

```c
void draw_image(IMAGE_BUFFER* buffer, const void* image,
                int32_t dest_x, int32_t dest_y,
                int32_t src_x, int32_t src_y, uint32_t width, uint32_t height,
                void* cap, uint8_t alpha, const PALETTE* palette);
```

| Parameter | Meaning |
|---|---|
| `buffer` | Destination framebuffer or clip view |
| `image` | Encoded image data. Must be 4-byte aligned |
| `dest_x, dest_y` | Where the source rectangle's top left corner lands in the buffer (may be negative or off-buffer) |
| `src_x, src_y, width, height` | Rectangle of the image to draw. Use `0, 0` and the image size for the whole image. A negative source position shifts the drawing right/down |
| `cap` | Capture buffer to save overwritten pixels into, or `NULL` |
| `alpha` | Global opacity, 0-255. 255 draws normally, 0 draws nothing |
| `palette` | Palette to use instead of the image's own, or `NULL`. Required for shared palette images |

Everything is clipped to the image, the destination buffer and the image's
stored rows. Drawing completely off-buffer is safe and does nothing.

### Alpha masks

`draw_alpha_mask()` draws an uncompressed 8-bit alpha mask (eg: a font
glyph) in a solid RGB565 color:

```c
void draw_alpha_mask(IMAGE_BUFFER* buffer, int32_t dest_x, int32_t dest_y,
                     const uint8_t* mask, uint32_t mask_stride,
                     uint32_t width, uint32_t height,
                     uint16_t color, uint8_t alpha);
```

The mask is `width` x `height` bytes, `mask_stride` bytes per row, with 0
transparent and 255 solid. `alpha` fades the whole mask (255 = coverage
only). To draw a glyph from a font atlas, point at it within the atlas:

```c
const uint8_t* g = atlas + glyph->y * atlas_stride + glyph->x;
draw_alpha_mask(&view, pen_x + glyph->ox, pen_y + glyph->oy,
                g, atlas_stride, glyph->w, glyph->h, color, 255);
```

The mask is clipped to the buffer, so to clip text to a region draw into a
`clip_image_buffer()` view. It's optimized for speed: empty and solid runs
are handled four pixels at a time, and partial coverage is blended with a
single multiply per pixel at 33 levels. Coverage 0 and 255 are exact; partly
covered pixels can be off by up to 1.5 RGB565 steps.

### Capture and restore

```c
size_t size = get_capture_size(cursor);        // worst case, from the image header
void* saved = malloc(size);                    // or a static buffer

draw_image(&screen, cursor, x, y, 0, 0, w, h, saved, 255, NULL);
// ... later ...
restore_image(&screen, saved);                 // put back what was underneath
```

- Only the pixels the image actually changes are saved. Fully transparent
  areas aren't touched, so they aren't saved.
- A capture is always valid after `draw_image()` returns, even if nothing
  was drawn, so it's always safe to restore.
- Restore into the same `IMAGE_BUFFER` (or clip view) that was drawn into.
  Saved positions are relative to it.
- When overlays overlap, restore them in the reverse order they were drawn.

### Palettes and recoloring

Palettes are stored ready for drawing: opaque entries hold the RGB565 value
and partially transparent entries hold premultiplied ARGB8888. To change
colors at runtime, copy the image's palette into RAM, modify it, and pass
it to `draw_image()`:

```c
const PALETTE* src = get_image_palette(icon);         // NULL for shared palette images
size_t bytes = sizeof(PALETTE) + src->count * sizeof(uint32_t);
PALETTE* tinted = malloc(bytes);
memcpy(tinted, src, bytes);

// Map the red channel of the original onto a black to orange gradient
recolor_palette(tinted, 0x000000, 0xFF8000, 16);

draw_image(&screen, icon, x, y, 0, 0, w, h, NULL, 255, tinted);
```

`recolor_palette(palette, colorA, colorB, channelShift)` reads one channel
of each entry (`channelShift` 16 = red, 8 = green, 0 = blue) and uses it to
interpolate between `colorA` (channel 0) and `colorB` (channel 255), keeping
each entry's alpha. Draw artwork in greyscale and it can be tinted to any
color, or any two-color gradient, at runtime.

To make other edits, `normalize_palette()` converts a palette to plain
straight-alpha ARGB8888, and `prepare_palette()` converts it back to the
drawing format. Converting there and back leaves a palette unchanged.

### Other functions

| Function | Purpose |
|---|---|
| `get_image_width(image)`, `get_image_height(image)` | Image size |
| `get_image_packed_size(image)` | Total encoded size in bytes |
| `get_capture_size(image)` | Capture buffer size needed for this image |
| `get_image_palette(image)` | The image's own palette, or `NULL` for shared palette images |
| `fill_rect(buffer, x, y, width, height, color)` | Fills a rectangle of a buffer with an RGB565 color, clipped to the buffer |
| `check_image_header(image, size)` | Validates the header, row table and palette against the available bytes. Use before trusting data from an untrusted source |
| `decode_image_argb8888(...)` | Decodes a whole image to ARGB8888 (see below) |
| `premultiply_argb8888(c)`, `unpremultiply_argb8888(c)` | Alpha conversion for single colors |
| `rgb565_to_rgb888(x)`, `rgb888_to_rgb565(x)` | Color conversion macros |

### Packs of images

`encoder/blobpack.js` combines several encoded images (or any other data)
into one file with an offset table. `src/blobpack.h` reads it:

```c
#include "blobpack.h"

const BLOBPACK* pack = (const BLOBPACK*)assets_bin;
const void* icon = get_blob(pack, 3);
uint32_t size = get_blob_size(pack, 3);
```

Each image starts at a 4-byte aligned offset as long as every image's size
is a multiple of 4. Pad them if not.

## Fonts and text

Fonts are rendered ahead of time at a fixed size to 8-bit coverage bitmaps
and packed into a single `.rfnt` blob holding the font metrics, glyph
info, kerning pairs, a codepoint hash table and the glyph bitmaps. Like
images, fonts are drawn straight from flash.

### Making a font

Render the glyphs with
[msdf-atlas-gen](https://github.com/Chlumsky/msdf-atlas-gen), then pack
its output:

```
msdf-atlas-gen -font MyFont.ttf -size 20 -type softmask -pxalign on -imageout myfont.png -json myfont.json
node encoder/cli.js myfont.json
```

- `-type softmask` renders anti-aliased coverage (`hardmask` also works,
  for aliased text). Distance field types aren't supported.
- `-size` is the size in pixels per em. Pack one font per size you need.
- `-pxalign on` puts each glyph on the pixel grid. Without it glyph
  positions are rounded and the packer warns.
- `-charset` or `-chars` picks the characters. The default is ASCII.
- Either `-yorigin` works.

The packer reads the atlas image named like the JSON file (or `--atlas`),
cuts each glyph out of the atlas, trims transparent edges, and shares
identical bitmaps. `--default-char` sets the character drawn in place of
characters the font doesn't have (default U+FFFD or `?`). From
JavaScript:

```js
import { packFontFiles } from "./encoder/font.js";
const font = await packFontFiles("myfont.json", "myfont.png", { defaultChar: "?" });
fs.writeFileSync("myfont.rfnt", font.data);
```

**Kerning:** msdf-atlas-gen only exports kerning from a font's legacy
`kern` table. Many modern fonts (eg: Inter, Roboto, Lato) only have GPOS
kerning, and come through without any kerning pairs. Fonts such as Open
Sans and PT Sans include a `kern` table.

### Drawing text

```c
const FONT* font = (const FONT*)myfont_rfnt;

int32_t pen = x * 64;                       // 1/64 pixels
const FONT_GLYPH* prev = NULL;
for (const char* p = text; *p; p++)
{
    const FONT_GLYPH* g = font_get_glyph(font, (uint8_t)*p);
    if (g == NULL)
        continue;
    pen += font_get_kerning(font, prev, g);
    draw_alpha_mask(&screen, ((pen + 32) >> 6) + g->left, baseline + g->top,
                    font_get_bitmap(font, g), g->width, g->width, g->height, color, 255);
    pen += g->advance;
    prev = g;
}
```

To clip text to a region, draw into a `clip_image_buffer()` view. To
center or right align text, measure it first:

```c
int32_t width = font_measure_text(font, "Hello", -1);
int32_t x = (screen_width - width) / 2;
```

| Function | Purpose |
|---|---|
| `font_find_glyph(font, codepoint)` | The glyph for a codepoint, or `NULL` |
| `font_get_glyph(font, codepoint)` | As above, falling back to the font's default glyph |
| `font_get_kerning(font, left, right)` | Advance adjustment for a glyph pair, in 1/64 pixels |
| `font_get_bitmap(font, glyph)` | The glyph's coverage bitmap (stride = width) |
| `font_measure_text(font, text, length)` | Width of a UTF-8 string in pixels (advances plus kerning, no wrapping). `length` in bytes, or -1 if NUL terminated |
| `check_font(font, size)` | Validates every offset, glyph, kerning pair and hash entry. Use before trusting a font from an untrusted source |

Glyph positions (`left`, `top`) are in pixels relative to the pen on the
baseline, with y down. Advances and kerning are in 1/64 pixels so spacing
stays accurate along a line. The `FONT` header has `lineHeight`,
`ascent`, `descent` and the underline position and thickness, in pixels.

## Decoding back to PNG or ARGB

For tools, previews and tests, both the C library and the JS encoder can
decode a whole image to 32-bit color:

- C: `decode_image_argb8888(image, image_size, palette, out, stride, premultiplied)`
  writes `0xAARRGGBB` pixels (BGRA byte order in memory), with straight or
  premultiplied alpha. It returns `false` for invalid data.
- JS: `unpackRle(buffer, { palette })` returns RGBA with straight alpha, and
  `unpackRleToPng()` writes a PNG. The CLI decodes `.rle565` inputs this way.

Both decoders check every read against the data size and reject corrupt,
truncated or malicious files instead of crashing. They produce identical
output, and opaque colors expand to full 8-bit range (RGB565 white decodes
to `#FFFFFF`).

These are for tooling, not for drawing on a device. Use `draw_image()` for
that.

## File format

All values are little endian. An encoded image is one contiguous block:

```
IMAGE_RLE header           40 bytes
row offset table           rowCount × uint32
palette (optional)         uint32 count, then count × uint32 entries
row data                   one entry per stored row
```

### Header

| Offset | Field | Description |
|---|---|---|
| 0 | `signature` | `0x35363552`, the bytes `R565` |
| 4 | `format` | `1` (`IMAGE_FORMAT_RLE`) |
| 8 | `width` | Image width in pixels |
| 12 | `height` | Image height in pixels |
| 16 | `flags` | `DRAW_FLAGS_ALPHA_PIXELS` (0x01) if any palette entry is partially transparent; `DRAW_FLAGS_LARGE_PALETTE` (0x02) if the palette has more than 256 entries |
| 20 | `packedSize` | Total size of the encoded image in bytes |
| 24 | `captureSize` | Worst case capture buffer size in bytes |
| 28 | `paletteOffset` | Offset of the palette from the start of the image, or 0 for a shared palette |
| 32 | `firstRow` | First stored row. Rows above it are fully transparent |
| 36 | `rowCount` | Number of stored rows. Rows below `firstRow + rowCount` are fully transparent |

The row offset table follows the header, holding the offset of each stored
row's data from the start of the image. Drawing can therefore start at any
row without reading the ones above it.

### Palette entries

Each entry is a 32-bit value in one of three forms:

| Entry | Meaning |
|---|---|
| `0x00000000` | Fully transparent |
| `0xFF00RRRR` | Opaque. The low 16 bits are the RGB565 color, written straight to the framebuffer |
| `0xAARRGGBB` (alpha 1-254) | Partially transparent, premultiplied 8-bit color |

The encoder sorts the palette by how often each color is used, so the most
common colors have the smallest indices.

### Row data

```
varlen  runCount
run     runs[runCount]
```

Each run starts with a varlen header:

| Run type | Header | Followed by |
|---|---|---|
| RLE (repeated pixel) | `(count << 1) \| 1` | One palette index |
| Literal, when `ALPHA_PIXELS` isn't set | `count << 1` | `count` palette indices |
| Literal, when `ALPHA_PIXELS` is set | `(count << 2) \| (alpha << 1)` | `count` palette indices. `alpha` is 0 if every pixel in the run is opaque |

- Palette indices are 1 byte when the palette has 256 entries or fewer,
  otherwise varlen.
- A row's runs cover the full image width.
- The encoder stores repeated pixels as RLE runs, and gathers short runs
  (2 pixels or fewer) of the same alpha type into literal runs. Transparent
  pixels are always in RLE runs so they can be skipped quickly.

**varlen** numbers are big endian groups of 7 bits. Every byte except the
last has its top bit (0x80) set. For example, 300 = `0x82 0x2C`.

### Capture buffer

A capture is a list of spans, ended by a span with offset 0 and count 0:

```
uint32  offset        byte offset from the start of the IMAGE_BUFFER's pixels
uint16  pixelCount
uint16  pixels[pixelCount]
```

### Font format

A font (`FONT` in `rle565.h`) is one 4-byte aligned block:

```
FONT header                52 bytes, signature "RFNT"
FONT_GLYPH[glyphCount]     24 bytes each, sorted by codepoint
FONT_KERNING[kerningCount] 4 bytes each: right glyph index, adjustment
hash table                 (1 << hashBits) × uint16 glyph index
glyph bitmaps              width × height bytes each
```

Each glyph has its codepoint, bitmap offset and size, position, advance,
and the range of kerning pairs with it on the left (sorted by the right
glyph, so lookups are a binary search).

The hash table maps codepoints to glyph indexes. A lookup starts at slot
`(codepoint * 0x9E3779B1) >> (32 - hashBits)` and steps forward,
wrapping, until it finds a glyph with that codepoint or an empty slot
(`0xFFFF`). The table is a power of two at least twice the glyph count, so
it's at most half full and lookups are short.

## How rendering works

`draw_image()` clips the request, then chooses one of 32 drawing loops based
on five flags:

| Flag | Set when |
|---|---|
| `ALPHA_PIXELS` | The image has partially transparent palette entries |
| `LARGE_PALETTE` | The image has more than 256 colors (varlen indices) |
| `ALPHA_BLEND` | The draw call's `alpha` is less than 255 |
| `XCLIP` | Only part of each row is drawn |
| `CAPTURE` | A capture buffer was supplied |

Each loop contains only the code its combination needs. The common case of
an opaque image drawn whole comes down to reading runs and storing palette
values. The loops are generated by `src/gencore.js` into
`src/rle565.core.h`. Don't edit the generated file; change the generator and
re-run it from the repository root:

```
node src/gencore.js
```

Rows above `firstRow` and below `firstRow + rowCount` are skipped entirely,
and transparent runs advance the output position without reading or writing
the framebuffer.

Blending works in each color channel's native precision and rounds to
nearest. Blending a color over itself leaves it unchanged, and an almost
fully transparent pixel doesn't darken what's underneath.

## Building and testing

### C tests

`test/main.cpp` draws a series of scenarios (clipping, fading, offsets,
recoloring, capture/restore) into an 800×480 buffer, writes each as
`test/build/NN.bmp` to look at, and then runs automated checks:

- clipping never writes outside the destination or clip view
- capture never exceeds `get_capture_size()` and restore is exact
- the decoder matches `draw_image()` exactly
- truncated and corrupted files are rejected safely
- header validation
- color conversion round trips and blend accuracy
- `fill_rect()` and `draw_alpha_mask()` clipping and blend accuracy
- font lookups, kerning and validation, including randomly damaged fonts

It also renders sample text to `test/build/font.bmp`.

It's built with the `mk` build tool (`test/test.mk.js`, MSVC toolchain):

```
cd test
mk
build\x64\debug\bin\test.exe
```

Run it from the `test` directory so it finds `artwork/`. It prints PASS or
FAIL for each check and exits non-zero on failure.

The library itself builds with any C99 compiler. The test program uses a
few MSVC specific features (`malloc.h`, `#pragma warning`).

## Requirements and limitations

- **Little endian, 4-byte alignment.** The renderer reads the header and row
  table directly as `uint32_t`, so images must be 4-byte aligned in memory
  and the CPU must be little endian. The structures use `#pragma pack(1)`,
  supported by MSVC, GCC and Clang.
- **RGB565 only.** The renderer draws into 16-bit RGB565 buffers in native
  byte order. Displays that need byte-swapped RGB565 must swap when
  transferring the buffer.
- **Encoding rounds down.** The encoder converts 8-bit color to RGB565 by
  truncation, so colors may be up to one RGB565 step darker than the source.
  Use `quantizePngTo565()` to preview the exact result.
- **Shared palette images need their palette.** They can't be drawn or
  previewed without it, including in the WIC codec.
- **Large palettes are slower.** Images with more than 256 colors use
  variable length indices. Reducing colors, or baking edges over a known
  background, keeps palettes small.
- **Fonts are a fixed size.** Each `.rfnt` is one size, and kerning comes
  only from the font's legacy `kern` table (see [Fonts and text](#fonts-and-text)).
- **The WIC codec** is built for x64 and x86. ARM64 isn't configured.
